## 全体像 — 3 層でどう配分するか（土台から固めろ）

> **本質：空間データという希少資源を、3 層でどう配分するかの話。それ以上でもそれ以下でもない。**

| 層 | 役割（たとえ） | やること | 本書 |
|---|---|---|---|
| **DB（土台）** | 金融政策 | `geography` で正しく距離を測り、`ST_DWithin` + GiST で配る | §1 |
| **NestJS（関所）** | 財政・ガバナンス | 外部 API の唯一の入口。キーを握り、クォータで上限を構造で縛る | §2 / §6 |
| **Next.js（民間）** | 需要側 | サーバ既定＋地図だけ特区。UX を「ハンコ制」と「ルール制」に仕分ける | §2 / §3 |

**→ どうするか：土台（DB）が歪むと上物が全部狂う。逆は後から直せる。だから §1 の DB から順に固める。** これが実装順の唯一の根拠。

## 1. 半径検索 — まず数字を置く

- 500件。1件の距離計算は三角関数数発 ≒ 数十ナノ秒。全件走査でも **数十マイクロ秒**。
- GiST インデックスがこの N で効く量は **実質ゼロ**。
- **結論：性能問題は存在しない。** 「PostGIS を性能で語る」のは嘘になる。

### 決定
それでも `ST_DWithin` を採用する。理由は性能ではなく **「スケール時の正解形を今あえて選べる、というデータ設計判断の提示」**。

```sql
-- geometry でなく geography。km 指定がそのまま通り、緯度で歪まない。
SELECT id, name,
       ST_Y(geom::geometry) AS lat,
       ST_X(geom::geometry) AS lng
FROM spots
WHERE ST_DWithin(geom, ST_MakePoint($lng, $lat)::geography, $radius_m)
ORDER BY geom <-> ST_MakePoint($lng, $lat)::geography;  -- 近い順
```

- カラム：`geom geography(Point, 4326)` + GiST インデックス。
- インデックスは「効くから」ではなく「正しいから」張る。

## 2. 逆ジオコーディング — 律速はここ。コストを計算する

Google Geocoding API：**$5 / 1,000 コール、無料枠 $200/月 = 40,000 コール/月**。

### 素朴実装の破綻（数量）
地図移動イベントごとに叩くと、能動的にパンする 1 ユーザーが毎分 ~100 の異なる中心 → **10分で 1,000 コール**。数人で無料枠が数十分で蒸発する。これは設計ミスであって仕様ではない。

### 削る（各段の効果）

| 施策 | 効果 |
|---|---|
| `idle` イベントのみで発火（`move` 中は叩かない） | ドラッグ中の数百コール → 停止後 1 |
| 400ms デバウンス | 微小停止の重複を吸収 |
| 中心が前回から **< 50m** なら発火しない（閾値ガード） | 手ブレ相当の無駄コールを 0 に |
| 座標を約 100m グリッドに丸めてキー化 → **valkey に共有キャッシュ** | 近接再訪・ユーザー横断で重複排除 |

- 結果：律速コールが **能動操作でも毎分 1〜3、キャッシュヒット後は実質 0**。**20〜60 倍の削減。**
- 「歓迎要件」の 3 項目（呼び出し抑制・キャッシュ・微小移動で叩かない）は、この **1 本の数量モデルの副産物**として説明する。バラバラの小技として書かない。

### 本質（飾らず 1 文＋1 不等式で書く）

> **外部 API を叩く回数を、ユーザーが実際に立ち止まった「新しい場所の数」まで落とす。**

手段は 3 つの間引きだけ。正体は枯れた概念で、新規性はない（飾ると本質から遠ざかる）。

| 名前 | 実体 | 制御軸 |
|---|---|---|
| debounce | ローパスフィルタ | 時間 |
| 距離閾値（θ=50m） | デッドバンド（不感帯） | 距離（空間） |
| キャッシュ | メモ化 | 記憶 |

コスト上界（証明不要、設計目標を不等式で書いただけ）：

```
叩く回数 ≤ その区間で訪れた「互いに θ 以上離れた安定地点」の数
```

- **θ = 50m で確定。** 根拠は住所（町丁目）が変わる典型スケール／日本の住所粒度。ここが README で根拠を語るべき唯一のパラメータ。
- **キャッシュは NestJS 側（valkey 共有）に置く。** ユーザー横断で効かせる。フロントは時間・距離の間引きだけ（叩く前に落とす）。二層で役割が割れる。→ 詳細は §6。

## 3. Next.js 層 — サーバかクライアントか

> **本質：Next.js は「サーバとクライアント、どっちで計算するか」を決めるだけの道具。それ以外は枝葉。**

App Router のデフォルトは**全部サーバ**（Server Component）。`'use client'` と書いた所だけが民間（ブラウザ）に降りる。

- **サーバ = 中央・公共部門**：計算も秘密（API キー・DB 接続）もここに置けば、漏れない・速い・バンドルが太らない。
- **`'use client'` = 特区（規制緩和）**：現場裁量が要る所だけ例外的に開放。降ろすほど重く・漏れやすくなる。
- 原則：**中央管理を既定に、特区は必要最小限。** 「なんでも `'use client'`」は統制なき民営化で、太って漏れる。

### → どうするか（部品を仕分ける）

| 部品 | どっち | 理由 |
|---|---|---|
| 地図・半径スライダー・地図移動の検知 | **`'use client'`（特区）** | インタラクティブ。ブラウザでしか動かない |
| スポット一覧の初期取得 | **サーバ既定** | データ取得はサーバで完結。速い |
| 逆ジオコーディング呼び出し | **サーバ（Route Handler）** | **API キーを絶対クライアントに出さない** ＝ §6 の「単一の関所」と一致 |

**境界は小さく切る。** 地図まわりだけをクライアントの島にし、外側はサーバのまま。秘密は中央に留まり、重いのは地図の島だけ。

### N=500 の含意 — ここで一段削る

- 500 件 × ~200B = **約 100KB（gzip で ~30KB）**。**全件がブラウザに載る。**
- 地図移動あたりの半径フィルタは **クライアントの純計算**で完結できる。バックエンド往復ゼロ、レイテンシゼロ。
- **決定**：サーバの `ST_DWithin` を「正解経路」として実装し、それを使う。**同時に「500 件ならクライアント短絡が最適」というトレードオフを README に明記する。** 実装は正解形、判断は言語化。両取り。

## 4. 削る — サービス構成

課題が要求するのは **FE + API + DB** の 3 つ。目的関数に対して各サービスの限界効用を 1 つずつ問う。

| サービス | この課題への貢献 | 判定 |
|---|---|---|
| frontend / backend / db | 要件そのもの | **残す** |
| cache (valkey) | §2 のコスト削減に直結 | **残す（理由が明確）** |

## 5. README = why だけ

コードで「何を」は読める。README に書くのは「なぜ」だけ。

1. PostGIS は性能でなく設計シグナルとして採用した
2. 律速は geocoding コール。数量モデルで削った

## 6. 制度設計 — コスト・ガバナンス

§2 の間引きは「期待コールを下げる緩和策」で、**フロントが正しく呼ぶ前提＝裁量依存**。担当者が変われば崩れる。制度設計はここを一段上に置く。

> **原則：気をつける設計ではなく、気をつけなくても済む設計。裁量を消し、構造（ルール）で保証する。**

数量設計と制度設計は両輪：

| | 役割 | 守るもの |
|---|---|---|
| 数量設計（§2） | 期待コールを下げる | 平常時の効率 |
| 制度設計（本節） | 最悪コールを上限で縛る＋劣化耐性 | 敵対時・担当者交代時の安全 |

### 規定

1. **単一の関所（鍵は外に出さない）**
   外部 geocoding は **NestJS のプロキシ 1 箇所だけ**が叩ける。API キーはクライアントに一切出さず `.env` 管理（リポジトリ禁止、`.env.example` を用意）。迂回路を塞ぐ。
2. **ハード枠（約束でなく構造）**
   プロキシに日次クォータ＋レートリミッタ。超過時は **キャッシュ返却か 429、外部は絶対に叩かない**。バグったフロントが連打しても予算は構造で守られる → §2 の不等式が「善意」でなく「構造」で成立。
3. **可視化＝台帳（隠れコストを表に）**
   外部コール数・キャッシュヒット率・クォータ消費をメトリクス/ログに出す。膨らむ隠れ負債を見える台帳に載せる（彼のバランスシート思想）。README に数値予算（$200/月＝40,000 コール）と実効上限を明記。
4. **インセンティブ整合（正しい道を唯一の道に）**
   生キーが無いので、間引き・キャッシュ入りのクライアント経由でしか呼べない。開発者は徳を要求されず、安い経路＝準拠経路。
5. **政策パラメータの明文化（1 箇所集約）**
   θ=50m / debounce=500ms / 日次クォータ は制度の政策パラメータ。設定 1 箇所に根拠付きで集約し、チューニングを「コード探し」でなく「ルール変更」にする。
6. **ロバスト性（次の担当者は本書を読まない前提）**
   安全は構造で担保する：キーは `.env.example`、シード投入は冪等で `docker-compose up` 一発、上限は関所で強制。
   - 先例：dev コンテナの root 所有ファイル問題を「毎回 chown」で運用せず、**uid1000 実行で構造的に再発を殺した**。症状の都度対応（裁量）でなくルール修正（制度）——同じ思想を全体へ。

---

## 結論

**機能を足す競争ではない。律速資源（geocoding コール）を数字で特定して削り（数量）、その上限を関所と台帳で構造的に縛り（制度）、規模（N=500）の含意を言語化し、要らないものを切る競争。**

- 数量だけだとバグ一発で無料枠が飛ぶ。制度だけだと平常時に無駄が残る。**両輪で「安くて、かつ壊れない」。**
- 要件を全部やることより、「何を・なぜやらなかったか」を数量・トレードオフ・構造で語れることが、この課題の本質。
